# Planned Agent A → Runner B — technical handover transaction

**For planned succession only.** This document teaches A WHAT technical reality to preserve and B HOW to reconstruct it. The transaction is **not** the optional Two-Pass/Three-Pass reasoning flow. V3.2 native `plan_handover.py` / `handover_context.py` and the existing handover-context schema remain the actual transaction; do not fork them or add another YAML schema merely for Buddy.

## 1. Timing and informational order

Agent A is still doing normal engineering. It may have asked **Time for Runner** at approximately 70% estimated episode life. B is working on an **independent Stage 1 plan** from original source/Owner WHAT/WHY without A's HOW. The technical handover packet is for a later disclosure; do not hand it to B early.

**Required distinction:** a Stage 1 Runner plan explains what B independently *would* build; the handover records what A actually *did*; Stage 2 checks both against current source. Handover is not a copy-paste plan of future work.

If Stage 1 was never independently sealed or B already saw A's implementation, normal technical handover can still proceed, but no one may call it a successful *blind Buddy Runner*.

## 2. Agent A — WHAT to record from real technical evidence

Within the existing governed issue and authorized native handover transaction, identify:

1. **Responsibility and authority:** exact Owner intent and accepted amendments; original issue/claim; existing EP if relevant; scope, explicitly parked neighbours and Owner-owned text. Preserve verbatim Owner words when required.
2. **Source identity:** repo; original START (ACTUALLY observed or UNKNOWN); base branch/SHA; latest current branch/HEAD; whether clean/dirty; PR stack and ancestry; in-flight writes/merges; provider readback status and source-drift risk.
3. **Actual changed behavior:** changed paths, *functions/symbols*, callers and consumers; previous behavior, current behavior and WHY. Include app UI/backend/workers, CSV or evidence consumers where applicable. Distinguish implemented, proposed, deployed and tested.
4. **Design choices:** successful and rejected approaches, trade-offs, performance/storage figures and their exact input/workload, nondeterministic/negative results, root causes and costly dead ends. This may include Agent A's actual HOW; it is **Stage 2 only**.
5. **Golden/source evidence:** authentic fixture path/hash and correct positive/negative pairing; actual exact-head test command/outcome and runner scope; browser/Chromium real journey where required; incomplete or stale CI and missing oracles. Never convert “test did not run” to a code failure or a green badge to proven end-to-end behavior.
6. **Work inventory:** every semantic unit actually finished/unfinished with source/evidence; current blocker; next minimum action; dependencies, external ownership, Medium ROI parked, High ROI absorbed/not absorbed; what remains UNKNOWN.
7. **V3.2 continuity:** latest accepted material/evidence frontier, actual TASK_EVIDENCE, negative knowledge, producer/writer authority and provider readback. Agent A must not hand-author P/E/D/percentages or manufacture accepted progress.
8. **Unavailability contingency:** if A is already gone, a third-party source auditor may reconstruct these fields with explicit attribution **THIRD_PARTY_OBSERVED**, not “Agent A final plan,” and unknown in-flight effects remain UNKNOWN.

Prefer a concise source/consumer/change matrix over a long narrative that obscures exact authority or tests.

## 3. HOW to think about technical handover

**Agent A self-audit, not self-certification:**

- Work backward from each Owner acceptance result to the currently used consumer functions; identify changed behavior and *proof at the same source HEAD*. Do not list files as a substitute for tracing call sites.
- Compare each “done” assertion with accepted issue facts and *actual* source/CI/browser/provider observations. If no real positive oracle exists, label the result incomplete even when a benchmark looks promising.
- Ask what the successor could wrongly assume from the packet. State negative knowledge and the strongest counterexample for each risky mechanism.
- Record a bounded first successor action that can be proven independently. Do not prescribe that B must choose your exact architecture; preserve WHY and evidence.

**Runner B Stage 2, not passive transcription:**

- Re-read B's immutable Stage 1 reconstruction and actual disclosed source; independently inspect live changed symbols and downstream calls.
- For each material decision compare **Owner must-have ↔ B frozen hypothesis ↔ A chosen HOW ↔ independently observed current source/outcome**. Choose ACCEPT_B, ACCEPT_A, REVISE_BOTH, UNPROVEN, OUTDATED or OUT_OF_SCOPE with an explicit falsifier.
- Identify both agents' missing requirements and what the original user can *actually do* in the real application; a source test is not necessarily deployed acceptance.
- Form a reconciled bounded next unit with legitimate source permissions, genuine tests and ROI triage. Do not edit B's sealed plan to make it look prophetic.
- Before coding: verify current HEAD **again** and ensure Agent A's write authority is actually ended/fenced under the existing controller/Owner policy and B is the authorized executor. A new chat is not a new approved EP.

## 4. Native transaction sequence — no new files required by the schema

1. Agent A continues engineering and checkpoints meaningful unrecorded knowledge using existing `TASK_EVIDENCE`. The Owner's “Prepare for runner” command is preparation, not a new accepted event or progress unit.
2. At the planned transfer point, run/complete the **existing authorized native `PLAN_HANDOVER` transaction**, including `HANDOVER_CONTEXT` source basis and native `HANDOVER_PLANNED` custody record. Use actual producer material, not a synthetic packet represented as official truth.
3. Check source/provider readback. A handover view is a *historical snapshot* and cannot outrank changed live source.
4. If Buddy Stage 1 is actually frozen and its visibility boundary proven, allow Runner B to read this technical packet and Stage 2 thinking prompt. Otherwise ordinary handover still works, with `BUDDY_INDEPENDENCE=NOT_PROVEN`.
5. B's critical reconciliation belongs to the continuing responsibility. A successor identity does not create a duplicate issue/EP, new Owner approval hurdle or automatic accepted progress.
6. Transfer the writer only through existing explicit governed assignment/lease fencing. If unavailable, keep the handover/read-only plan and report the source and authority blocker.

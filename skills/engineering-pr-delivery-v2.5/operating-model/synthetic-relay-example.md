# Synthetic V2.5 relay walkthrough

## Purpose

This example shows the minimum durable story an ACTIVE serial relay must communicate. It is repository-neutral and illustrative: use the schemas/templates for exact machine fields and the synthetic test suite for executable fixtures.

## Scenario

A generic project has a command-line configuration loader. The current roadmap work package is to reject duplicate keys while preserving existing canonical parsing behavior.

```text
Objective OBJ-01  Reliable configuration loading
  └─ Phase PH-02  Validation semantics
       └─ WP-02   Reject duplicate keys                CURRENT FRONTIER
            └─ EP-0002
```

The predecessor completed `WP-01` and left `CP-0001` plus `EP-0002`.

## What the outgoing agent must persist

### Context capsule

```text
product_goal: deterministic configuration loading
roadmap_position: OBJ-01 / PH-02 / WP-02
why_this_work_exists: duplicate keys currently resolve implicitly and can hide operator mistakes
current_architecture: parser produces ordered key/value records; validator owns semantic rejection
prior_owner_decisions: preserve accepted single-key behavior and error format
known_problem: duplicate-key path lacks explicit validation
non_goal: no parser rewrite, no format redesign, no unrelated cleanup
```

### Typed input

```yaml
id: INPUT-01
name: duplicate-key policy
authority: OWNER_DECISION
source: ODR-0001
value: reject duplicates before canonical config construction
value_type: policy
applicability: CURRENT_EP_REQUIRED
editability: IMMUTABLE_AUTHORITY
resolution: READY
required_for:
  acceptance: [AC-02]
  tests: [TEST-02]
  steps: [STEP-02]
```

### Independent oracle

```yaml
id: ORACLE-01
type: REFERENCE_DATA
purpose: prove duplicate rejection without using the implementation under test as its own oracle
source: tests/reference/duplicate-key-cases.yaml
payload: two duplicate-key fixtures plus one unique-key control
expected: duplicates fail with the documented error; unique-key control remains accepted
oracle_class: FROZEN_GOLDEN
independence: maintained separately from production parser logic
applicability: CURRENT_EP_REQUIRED
resolution: READY
required_for:
  acceptance: [AC-01, AC-02]
  tests: [TEST-01, TEST-02]
```

### Executable discovery

```yaml
- id: DSTEP-01
  action: TRACE
  target: src/config/
  question: Where does parsed input become canonical configuration state?
  expected_outputs: [production_path, state_owner]
  receipt_required: true
  stop_if: More than one unresolved state owner remains.

- id: DSTEP-02
  action: VERIFY
  target: tests/reference/duplicate-key-cases.yaml
  question: Is ORACLE-01 independent of the production validator being changed?
  expected_outputs: [oracle_independence_basis]
  receipt_required: true
  stop_if: The oracle is generated by the implementation under test.
```

### Scope

```text
allowed_write:
  - src/config/validator.*
  - tests/config/duplicate_keys.*
allowed_read:
  - src/config/**
  - tests/reference/**
protected:
  - accepted behavior for unique keys
  - documented error envelope
prohibited:
  - parser rewrite
  - configuration-format redesign
  - unrelated refactor
owner_reserved:
  - changing duplicate-key policy from reject to last-write-wins
```

### Ordered work

```text
STEP-01 trace current production path and freeze before-change test evidence
STEP-02 add duplicate detection in the existing validator owner
STEP-03 run unique-key regression plus duplicate-key oracle cases
STEP-04 complete routed quality review and checkpoint evidence
```

Each step references its concrete targets, inputs, acceptance criteria, tests/oracles, expected intermediate result, and stop conditions.

### Quality routing

```yaml
applicable:
  - blueprint: software-design
    reason: validator ownership and error propagation are material
    review_focus: preserve the existing parser/validator responsibility boundary
  - blueprint: coding
    reason: production validation logic changes
    review_focus: bounded duplicate detection with no parser rewrite
  - blueprint: testing
    reason: behavior changes and regression evidence is required
    review_focus: duplicate failure plus unique-key control
not_applicable:
  - blueprint: engineering-numerics
    reason: no numerical authority or method changes
```

The full built-in quality library must be partitioned exactly once; the abbreviated list above only illustrates the distinction.

## Incoming candidate takeover

The incoming candidate receives only the repository.

```text
REPO_STATE
  ↓
roadmap / frontier
  ↓
EP-0002 + CP-0001
  ↓
DSTEP-01 / DSTEP-02 execution
  ↓
DISC-0002
```

Suppose entering `PH-02` is a fresh qualification boundary. The repository also contains `QSET-0002`.

A valid candidate answers from repository state:

```text
Q1 production path:
   parser -> ordered records -> validator -> canonical configuration

Q2 engineering problem:
   duplicate keys currently pass through the validator and are resolved implicitly downstream;
   the required behavior is explicit rejection before canonical state construction

Q3 boundary/invariant/falsifier:
   mutate validator only; preserve unique-key acceptance and error envelope;
   falsifier = any duplicate case accepted or any unique-key control rejected

Q4 independent verification:
   run ORACLE-01 frozen reference cases plus existing unique-key regression

Q5 first safe slice:
   add duplicate detection at validator entry and run TEST-01/TEST-02 before any broader cleanup
```

An independent evaluator records `QUAL-0002` PASS. `TC-0002` then binds candidate, route, roadmap revision, material ref, semantic EP digest, profile digest, predecessor digest, `DISC-0002`, and `QUAL-0002`.

Only then can live `MATERIAL_WRITE_READY` become true, and only if the checked-out branch/material basis, drift/continuity state, execution plane, material authority, and stop plane also permit WRITE.

## Completion and recursive handover

After implementation:

```text
TEST-01 unique-key regression              PASS
TEST-02 duplicate-key frozen oracle        PASS
QRV-0002 applicable quality procedures     CLEAR / evidence recorded
CP-0002                                    records exact material basis
PROGRESS                                   recalculated
ISSUE_GRAPH                                reconciled if required
frontier                                   recomputed
EP-0003 or terminal disposition            persisted
```

If `WP-03` is next, the outgoing agent creates a semantic `EP-0003` and a fresh `QSET-0003` only when the phase/material qualification boundary requires it. The next candidate repeats repository-only DISC/QUAL/TC admission.

## Failure cases this example is designed to prevent

- “Check the parser and fix duplicates” with no production-path discovery is a hollow EP.
- A future-step input marked unavailable must not block the current slice unless its applicability says it is currently required.
- A test produced by the changed validator is not automatically an independent oracle.
- ACTIVE lifecycle or persisted WRITE is not candidate write permission.
- Ordinary quality findings or NOT_RUN evidence are not automatically hard stops.
- An issue comment or generated handover cannot override roadmap/EP/checkpoint authority.
- Prior chat cannot be required to explain the task, scope, evidence, first action, or successor work.

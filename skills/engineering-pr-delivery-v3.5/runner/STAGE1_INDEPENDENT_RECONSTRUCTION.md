## 1. First think about the historical system — **NO SOLUTION YET**

**Order is mandatory.** Run Part A from the separately released historical, source-pinned intake. Even if the original Owner task was already provided, treat this as `TASK_AWARE_HISTORICAL_BASELINE`, not the task-blind Two-Pass generator. Write a substantive factual baseline **before** stating alternatives, ROI, code changes or a plan.

**WHAT to investigate:** Which original user-facing output does the application produce? What is the authoritative input? At the allowed historical SHA, trace a concrete input → source producer/function → transforms and identities → real downstream consumer/function → observable result. Which invariant explains correct handling of a changed alias, occurrence, owner, branch, configuration or provider revision? What is unobservable and why?

**HOW to investigate:** Read pinned source symbols and callers at their true commit; trace **backward from the final output** and **forward from original input**. Work one genuine positive input/output witness and one meaningful changed-boundary or negative variation *if authentic material exists*. Cite actual source paths/symbols, fixture hashes, observed result and exact uncertainty. If materials or executable browser are inaccessible, say `NOT_OBSERVED` / `NOT_RUN`; never invent a golden or assert current application acceptance from historical tests.

### Worked example — good first result versus premature patch

**Insufficient:** "Use a sparse JSON catalog, then refactor its Worker." That selects a fix without showing the current consumer semantics.

**Appropriate Part A:** "At historical SHA [actual SHA], [actual producer path:function] reads [input identity] that [actual consumer path:function] uses to form [output]. Fixture [authentic hash] demonstrates [actual observation]; changing ancestor/alias [original changed case] produces [actual result or NOT_RUN]. The latest Agent A implementation is UNKNOWN. **I have not chosen a fix.**"

**Part A STOP:** Do not list PRs, new schemas, alternative implementations, an implementation issue, Owner plan amendments, priority ranks, or Agent A's selected risks until the factual baseline is written. A generic inventory of files fails this gate.

## 2. Then think independently about the *original approved problem*

Once Part A is complete, use only original authenticated Owner WHAT/WHY and approved historical responsibility (the Stage 1 packet may already include them), plus **your own observed baseline**. Do not use Agent A's current PR, algorithm, amendments, evidence, shortlist of risks, parked Medium work or technical handover. If that information has leaked, mark `STAGE1_CONTAMINATED` and stop.

**WHAT:** Where does the original Owner outcome diverge from observed historical behavior? Is there a genuine missing causal seam or might the existing architecture be adequate? Which original consumer/identity/branch invariant matters? What user output and negative case could settle the disagreement? Which material fact is only visible in Stage 2?

**HOW:** Derive alternatives from the *observed consumer and falsifier*, not a preset requirement to invent two redesigns. Compare materially different approaches **when actually plausible**, including `NO_CHANGE` when justified. For each candidate, discuss the source invariant it would preserve, what would falsify it, the costs that are measured versus UNKNOWN, and the actual downstream positive/negative/browser oracle needed. Recommend a **provisional** High-ROI investigation or park a Medium-ROI alternative with revisit evidence. Do not copy a current plan or change an approved denominator.

**Worked example:** "A preprojection could be faster but might erase ancestor identity required by [historical consumer]. Retaining original bytes with bounded lookups is an alternative. I would first compare both final consumer outputs on an authentic same-name/different-parent fixture and changed configuration. Without that positive pairing, speed and correctness remain UNKNOWN." These are thinking patterns, not predetermined fixes.

**Stage 1 limits:** Do not publish a copy-ready current-head `IMPLEMENTATION_PLAN`, `PLAN_UPDATE`, child issue, source diff, merge or P/E. A detailed actionable plan belongs in Stage 2 **after** four-perspective source reconciliation and Owner approval. Preserve actual domain-derived questions; produce exactly three only when the governing successor/handover contract specifically requires that count.

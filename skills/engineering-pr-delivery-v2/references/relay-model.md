# Relay Engineering Model

## Purpose

Engineering work is a chain of durable repository endpoints, not a sequence of chat sessions.

The outgoing agent is never required for recovery. The repository owns the baton.

## Canonical repository layout

For new chains:

```text
agents/chains/<CHAIN_ID>/ACTIVE.md
agents/chains/<CHAIN_ID>/endpoints/<ENDPOINT_ID>.md
agents/qualifications/<CHAIN_ID>/<QUESTION_SET_ID>-<candidate>-answer.md
agents/qualifications/<CHAIN_ID>/<QUESTION_SET_ID>-<candidate>-verdict.md
```

Compatibility / derived dashboard:

```text
agents/agentchain.md
```

`ACTIVE.md` is the authoritative mutable current pointer for one chain. Detailed endpoints are immutable after durable creation. The shared dashboard is not required for normal chain advancement.

This means independent WRC, LAFEA, and LoadCalc chains do not create Git conflicts merely by advancing relay metadata.

## Work identity

```text
REPOSITORY
  -> CHAIN_ID
  -> LEG_ID
  -> ENDPOINT_ID
  -> PR / branch / commits
```

The globally meaningful endpoint identity is:

```text
(CHAIN_ID, ENDPOINT_ID)
```

`EP-0001` may therefore exist in many different chains.

- `CHAIN_ID` persists for the engineering mission even when PRs change.
- `LEG_ID` identifies one coherent contribution segment.
- `ENDPOINT_ID` identifies one immutable checkpoint within its chain.

## Relay state

Recommended states:

```text
ACTIVE
QUALIFICATION_REQUIRED
RECOVERY_REQUIRED
BLOCKED
READY_FOR_NEXT_LEG
COMPLETE
SUPERSEDED
```

A normal flow is:

```text
ACTIVE.md @ epoch N
  -> create immutable endpoint at epoch N+1
  -> compare-and-swap ACTIVE.md to epoch N+1
  -> qualification when custody changes
  -> qualified contribution
  -> next endpoint
```

Abrupt loss is:

```text
ACTIVE.md + latest durable endpoint
  -> agent disappears
  -> live re-ground
  -> recovery endpoint
  -> qualification
  -> compare-and-swap ACTIVE.md
```

No outgoing-agent release event is required.

## Chain-local current authority

`ACTIVE.md` contains current traffic/custody data for exactly one chain:

```text
CHAIN_ID
MISSION
ACTIVE_ENDPOINT
ACTIVE_ENDPOINT_FILE
PR
BRANCH
HEAD
STATE
AUTHORITY_DOMAIN
ACTIVE_CUSTODIAN
CUSTODY_EPOCH
COORDINATION_STATE
DEPENDENCIES
```

Other chains do not edit this file.

## Custody epoch

The first endpoint uses `CUSTODY_EPOCH: 1`. Every direct successor increments by exactly one.

A state update must use the exact prior repository version/blob of `ACTIVE.md`. A conflict or unexpected epoch is a stale-write signal and requires re-grounding.

Two successors from one endpoint are a custody divergence, not two equally authoritative next states.

## Endpoint authority

A completed detailed endpoint file is immutable.

If an earlier endpoint contains an error, a later endpoint records:

```text
SUPERSEDES_ENDPOINT:
SUPERSEDED_ASSERTION:
CORRECTED_STATE:
EVIDENCE:
```

`PREVIOUS_ENDPOINT` is chain-local and references the immediately preceding endpoint for that chain.

## Repository-wide visibility

Repository-wide traffic is discovered by scanning:

```text
agents/chains/*/ACTIVE.md
```

A convenience dashboard may be rendered with:

```text
python skills/engineering-pr-delivery-v2/scripts/render_agentchain_dashboard.py .
```

The dashboard is derived state. It may be stale without invalidating a chain's authoritative `ACTIVE.md`.

## Material state

The endpoint binds to repository material state through `CHECKPOINT_HEAD`.

Material state includes changes to:

- production behavior;
- tests/benchmarks/oracles;
- engineering input data;
- engineering source authority;
- numerical or physical conventions;
- behavior-changing configuration;
- result publication authority;
- engineering methodology.

Relay metadata-only changes do not create a new engineering material state by themselves.

## Crash safety

Work that exists only in private context, local unpushed workspace, or chat is not durable authority.

If an endpoint is created but `ACTIVE.md` is not advanced, treat it as an orphan durable artifact and reconcile it. If `ACTIVE.md` advancement fails because another agent changed the blob/epoch, re-ground rather than overwrite.

## Different-chain vs same-chain concurrency

Different chains:

```text
ADV-WRC-1389      -> its own ACTIVE.md
ADV-LAFEA-1422    -> its own ACTIVE.md
ADV-LOADCALC-1505 -> its own ACTIVE.md
```

No relay conflict is expected unless their actual engineering paths, authority, benchmarks, inputs, release domains, or dependencies overlap.

Same chain:

```text
one ACTIVE.md
one custody epoch sequence
one authoritative successor lineage
```

Concurrent same-chain advancement must reconcile before either branch is accepted as current.

## Completion states

Never collapse:

```text
AGENT_LEG_COMPLETE
PR_COMPLETE
CHAIN_COMPLETE
```

A merged PR may still leave the chain active. Terminal `ACTIVE.md` remains durable but is omitted from active dashboard output.

## Legacy compatibility

Existing `agents/agentchain.md` and `agents/agentchain/<CHAIN_ID>/**` artifacts remain historical/recovery evidence. New chains use the chain-local store; legacy chains may migrate deliberately rather than being mass-rewritten.

# V3B generic Physics agent execution and relay

Research rule: use [research freedom and minimum criteria](V3B-Research-and-Minimum-Criteria.md). Search and explore with a provisional gate outline; promote useful findings through a documented dependency delta. Do not wait for a fully accepted baseline to investigate or draft. Use flexible support and mark scientific uncertainties.

Publication execution: after preparing accepted baseline/source and authored product inputs, use the [Physics publication command](../ProductionKit/V3B-Publication-Input.md). It emits actual HTML/SVG and verifies their bytes and supported numerical answers. Do not infer academic approval from this bounded host.

Use this work order for any Physics topic. Fill the parameters from owner instructions and source evidence; do not infer owner authorization or measured knowledge. Read [the production blueprint](V3B-Production-Blueprint.md) and [acceptance contract](V3B-Acceptance-and-Regression.md) first.

## Reusable work order

> Prepare the requested Physics products under the V3B six-Core contract.
>
> Inputs: topic/subtopic scope; grade and curriculum/exam scope; selected Cores; frozen source locations and revisions; intrinsic difficulty/depth request; practice purpose; scoped knowledge evidence OR explicit owner waiver for 2A/2B; intended output medium; current gate baseline and predecessor packet, if any.
>
> Preserve frozen Core1/Core2 and source identity. Work only in the authorized V3B folder. Resolve contradictions visibly. If a required input is missing, identify the affected gate and continue independent useful work; never invent evidence to turn it green.
>
> Begin research and provisional prose from a scope/gate outline. Before accepted production, deliver the reconciled source inventory, scientific/prerequisite graph, required inference/representation obligations, gate proposal and cross-Core allocation/exposure plan. Show the owner board with separate evidence columns. Hold only work dependent on an unresolved gate.
>
> Author in 1–3-subtopic packets. Apply intrinsic difficulty to 1A/1B, and purpose plus knowledge/waiver controls to 2A/2B. Produce the actual explanations, scientific figures, prompts, graduated hints and complete answers required by each Core. Inventory every embedded prompt and retry. Do not substitute page counts, headings, coverage IDs or answer anchors for substantive content.
>
> Reuse scientific models and diagram templates only through compatible bindings. Declare intentional example reuse and demonstrate the changed reasoning demand of transfer items. Run all-pair screening against prior learner exposures. Retain equation meaning, assumptions, units, frame and sign conventions across products.
>
> Compare answers and figures with independent source/model expectations, including the actual published representations. Render and inspect the intended final medium. Report exact commands, input/output digests, observations, missing tools and checks not run. Never report a script that is absent or a result inferred from its name.
>
> Return the current packet, artifacts, evidence, unresolved issues and next action. Missing academic review, stale dependencies or missing publication inspection keep their own gates open. Only the owner can authorize release/merge. Do not edit other subjects until authorized.

## Roles, reuse and resource control

Roles are responsibilities, not a requirement to spawn a fresh agent at every step. The governor tracks scope, versions and acceptance. The source/model role grounds content. The author produces Core-specific teaching. The scientific reviewer checks equations/answers/figures; the pedagogy reviewer checks assimilation, repair and transfer; the publication reviewer inspects final artifacts.

Keep three decisions separate:

| Decision | Reuse allowed when | Fresh review or restart needed when |
|---|---|---|
| Specialist profile | Subject and required expertise fit | New domain/depth needs another qualified profile |
| Author instance | Context is intact, scope and baseline match, prior errors are resolved | Context is missing, drift persists, or a different baseline invalidates assumptions |
| Content/asset | Source, scientific model, learner action and relevant controls are compatible | Values, frame, purpose, dependencies or required support change |

Reuse the author for coherent continuation to reduce context transfer. The author cannot provide its own independent review; another qualified instance/person must inspect the evidence before independent review is marked complete. Fresh instances alone do not guarantee independence if they simply accept the author's summary or expected answers. Supply original evidence and require their own checks. Do not repeatedly retry failed generation without classifying the cause: source, scientific model, teaching allocation, rendering or validator defect.

## Portable packet: the next agent's actual working context

The packet envelope uses the existing packet contract plus this minimum payload:

- Topic, bucket IDs, selected Cores, product intent, intrinsic badges, learner controls and owner decisions with provenance.
- Exact source objects, original question/subpart text, data, options and figures; normalized atoms with source locators and unresolved extraction issues.
- Model, prerequisite/obligation graph, accepted baseline and policy versions, equation semantics and required inference steps.
- Per-Core allocation and exposure ledger, including examples already encountered in other buckets and answer sections.
- Actual authored content objects, diagram scenes/instances, answer records, publication artifacts, renderer/validator versions and runnable commands.
- Host-computed digest manifest, accepted evidence, failures/rejected revisions, open issues, predecessor packet IDs and exact next action.

Do not replace source questions with answers or a summary. Avoid indiscriminately copying the entire repository: bundle the dependency closure and accessible immutable references, then prove referenced bytes are available to the receiver. Secret/private access assumptions are not portable references.

The receiver verifies manifests and current predecessor/baseline versions before writing. It must reconstruct the required source/model/obligation state without relying on the originating chat. Test an actual restart with access only to the declared bundle. A promised fresh-agent check is NOT_RUN until performed. Conflicting output from a stale packet is retained as rejected evidence and cannot overwrite current accepted state.

## One authoritative current state

Each topic has one current-state pointer to an immutable release/work packet. Owner board, manifests and final reports derive their basis from it; historical receipts remain historical. Before accepting a return, verify packet predecessor, baseline, policy, source and artifact versions. Identical accepted output is idempotent; conflicting duplicates require reconciliation. Do not leave two files both claiming different current baselines.

For scope extensions, calculate the dependency delta first. Extend/review the gate baseline, then issue new work orders only for affected units. A depth change is not merely a longer page budget. Shared prerequisite or example exposure changes can affect apparently unrelated downstream products; include those edges in invalidation.

## Completion report

Report product-by-product readiness, actual artifact locations, checks run with exact scope, checks missing, academic/visual findings and the next blocking action. Separate documentation validity, machine verification, academic review, learner calibration and owner release. Never generalize one fixture's passing result to an untested scientific family or another topic.

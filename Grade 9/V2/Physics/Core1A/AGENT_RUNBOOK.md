# Core (1A) SBA Agent Runbook

This file is the **normative execution order** for any agent continuing Core (1A). Do not improvise the sequence. If this runbook conflicts with older prose guidance, this runbook, the executable production kit and the machine-validated contracts take precedence.

## Start here — executable path first

Before authoring or rendering a bucket, read these files in order:

1. `AGENT_RUNBOOK.md`
2. `README.md`
3. `CORE1A_UI_SPEC.md`
4. `SOURCE_COMPLETENESS_SPEC.md`
5. `registry/physics-core1a-motion-in-a-plane-build-state-v1.json`
6. `registry/physics-core1a-motion-in-a-plane-sba-v1.json`
7. `registry/physics-core1a-motion-in-a-plane-sba-publication-index-v1.json`
8. `registry/physics-core1a-scaffold-profiles-v1.json`
9. `registry/physics-core1a-core2-linkage.json`
10. the target bucket profile/transfer registry if one already exists.

Then **route the work through the production kit**:

```bash
python 'Grade 9/V2/Physics/Core1A/production_kit/task_router.py' \
  --prior 20 \
  --out /tmp/core1a-task.json
```

The router is authoritative for the next active bucket, difficulty, question load, prerequisite buckets, source-mode hint and scaffold profile. `engine/next_sba.py` remains a drift cross-check; it is not the primary production entry point.

For an explicit bucket during fixture/debug work:

```bash
python 'Grade 9/V2/Physics/Core1A/production_kit/task_router.py' \
  --bucket M2D-SBA-XX --prior 20 --out /tmp/core1a-task.json
```

A bucket is not ready for page planning until the production inputs exist and validate:

- **Source Contract** — source evidence, integrity class, permitted use, equations/validity, gaps and forbidden inventions.
- **Answer Contract** — exact Core (2) ownership/release, verified answer authority, solution skeleton, H1/H2/H3 semantic roles and verification checks.
- **Scaffold Profile** — difficulty × prior-knowledge requirements plus question-load scaling.
- **Authoring payload** — learning atoms and transfer families.

Build a normalized learner representation before rendering:

```bash
python 'Grade 9/V2/Physics/Core1A/production_kit/build_learning_representation.py' \
  --fixture <production-input.json> \
  --out /tmp/core1a-learning-representation.json

python 'Grade 9/V2/Physics/Core1A/production_kit/validate_learning_representation.py' \
  --fixture <production-input.json> \
  --input /tmp/core1a-learning-representation.json \
  --report /tmp/core1a-validation-report.json
```

**Stop if the validator fails. Do not render around a failed contract.**

The three golden fixtures are executable regression anchors, not prose examples to copy literally:

```bash
python 'Grade 9/V2/Physics/Core1A/production_kit/run_golden_fixtures.py'
```

They cover three materially different production shapes:

- `M2D-SBA-03` — LOW question load + a cross-bucket held question;
- `M2D-SBA-05` — VERY_HIGH load + seven distinct transfer families;
- `M2D-SBA-21` — SOURCE_VISIBLE_EXTENSION + explicit source gap / derived-bridge discipline.

## Non-negotiable architecture

Core (1) is semantic authority: **what must be taught**.

Core (1A) is the learner-assimilation layer: **how this bucket must be taught to the declared learner profile so that the learner can independently attempt the linked Core (2) questions**.

Core (1A) is not a prettier Core (1), not a summary sheet, and not a reverse-engineered answer key.

For the current queue, build dedicated PDFs only for buckets with one or more primary Revised Core (2) v2 questions. Buckets with zero primary questions remain in the SBA map but are `SKIP_NO_PRIMARY_CORE2`; `task_router.py` must reject them.

## Production contracts are binding

### Task contract

Generated by `production_kit/task_router.py`. It binds:
- bucket id;
- 20%/50% prior-knowledge profile;
- intrinsic difficulty;
- question-load class and minimum family count;
- prerequisites;
- source-mode hint;
- scaffold profile;
- required inputs/outputs;
- exact G0→G9 gate order.

### Source contract

Use `contracts/physics-core1a-source-contract.schema.json`.

Every used source item must carry an integrity class:
- `CLEAN`;
- `TYPOGRAPHIC_OCR_AMBIGUITY`;
- `MATHEMATICAL_DOMAIN_ISSUE`;
- `TRUNCATED_OR_AMBIGUOUS`.

A non-clean source may not be silently `USE`. Derived bridge equations require a declared derivation basis. `PRACTICE_DRIVEN` and `SOURCE_VISIBLE_EXTENSION` work must record source gaps; extensions must also declare forbidden inventions.

### Answer contract

Use `contracts/physics-core1a-answer-contract.schema.json`.

Do not invent an exact Core (2) answer to satisfy the contract. Use:
- `INLINE_VERIFIED` only when the canonical answer has been independently verified and can be stored safely;
- `EXTERNAL_VERIFIED` when the authoritative solution is referenced elsewhere.

H1/H2/H3 roles are fixed:
- H1 = `KEY_PHYSICS`;
- H2 = `REPRESENTATION`;
- H3 = `FIRST_MOVE`.

Every rung must point to an existing earlier learning atom.

### Scaffold profile

Use `registry/physics-core1a-scaffold-profiles-v1.json`, validated by `contracts/physics-core1a-scaffold-profiles.schema.json`.

Difficulty and prior knowledge are independent. Question load is a third independent control. The selected profile determines minimum visual staging, misconception policy, worked/completion support, independent practice and readiness requirements.

### Learning Representation (LR)

`build_learning_representation.py` compiles source contract + answer contract + scaffold + authoring atoms/families into one normalized LR. The LR is the renderer-facing instructional object. Do not render directly from ad-hoc prose notes.

The validator must prove at minimum:
- exact primary-question coverage;
- no duplicate question across families;
- source-integrity compliance;
- declared basis for derived bridges;
- scaffold visual depth;
- hint-preteach closure;
- attempt-before-hints;
- readiness-before-transfer;
- held-question prerequisites;
- golden-fixture expectations where applicable.

## Mandatory build state machine

Every active SBA bucket passes these gates in this exact order. A later gate must not be marked complete while an earlier gate is incomplete.

### G0 — INDEX_SYNC

Update the published SBA bucket table first.

Required evidence:
- target bucket exists in the canonical SBA registry;
- origin, teaching home, primary Core (2) questions and state match the canonical registry;
- the publication index is the first publication surface for the bucket sequence.

### G1 — SOURCE_AND_CORE2_AUDIT

Read the source/Core (1) basis and every primary Core (2) question plus H1/H2/H3 reveals. Materialize the result as **Source Contract + Answer Contract**, not only notes.

Required outputs:
- exact prerequisite concepts;
- all source equations/illustrations needed;
- every H1/H2/H3 reveal mapped to a proposed learning atom;
- source gaps or QC issues explicitly recorded rather than silently repaired.

### G2 — DIFFICULTY_AND_READINESS

Record intrinsic difficulty separately from learner readiness and select the machine scaffold profile.

Current priority learner profiles:
- 20% usable prior knowledge;
- 50% usable prior knowledge.

For 20% learners, assume vocabulary, representation choice, sign convention, prerequisite recall and equation selection may all be fragile unless explicitly checked.

### G3 — LEARNING_ATOM_DECOMPOSITION

Decompose the bucket into the smallest meaningful teaching atoms.

Each atom requires:
- purpose;
- prerequisite support;
- staged teaching moves;
- visual-stage count;
- misconception targets;
- at least one check.

Rule: **harder concept or lower readiness = more pictures and fewer inferential jumps, not denser text**.

### G4 — CORE2_HINT_PRETEACH_AUDIT

Every primary Core (2) question must have H1/H2/H3 mapped to earlier Core (1A) teaching evidence.

- H1 = key physics already taught;
- H2 = representation/model already taught;
- H3 = first mathematical move already demonstrated or practised.

If any reveal is new in Core (2), the Core (1A) bucket is incomplete. The production validator must fail such a mapping.

Question release may be delayed by another prerequisite bucket.

### G5 — PROBLEM_FAMILY_ASSIMILATION

Do not map many Core (2) questions as one undifferentiated list. Cluster them into **problem families** with distinct recognition and solution routines.

Question-load planning rule is encoded in the scaffold registry:
- 1–2 primary questions: LOW;
- 3–5: MEDIUM;
- 6–9: HIGH;
- 10+: VERY_HIGH.

A transfer routine must contain:
1. `LOOK FOR` / recognition signals;
2. numbered STEP 1 → STEP N method;
3. one fully worked or already-taught analogue before independence;
4. **INDEPENDENT PRACTICE** with blank attempt space or equivalent attempt-first presentation;
5. H1/H2/H3 optional hints after the attempt, not pre-exposed as a mini-solution;
6. `READY TO MOVE ON?` gate;
7. exact Core (2) release targets.

### G6 — PAGE_PLAN

Compile and validate the LR **before** page design. The publication plan must be explicit before rendering.

For a 20% learner, use this macro-order unless a documented reason requires otherwise:

`SBA INDEX → FOUNDATION/PRETRAINING → CONCEPT BUILD → PICTORIAL STAGES → PICTURE-TO-MATHS → MISCONCEPTION → WATCH ONE → COMPLETE ONE → PROBLEM-FAMILY ROUTINE(S) → INDEPENDENT PRACTICE → HINTS → READINESS → CORE (2) TRANSFER SUMMARY`

For HIGH/VERY_HIGH question load, the transfer section must grow with the number of distinct problem families; do not compress 10+ questions into one end-page list.

### G7 — RENDER_AND_VISUAL_AUDIT

Render from the validated LR/publication plan, then render the PDF to page images and inspect all pages.

Reject:
- clipped titles/badges;
- label collisions;
- raw math strings;
- text below font floors;
- unexplained equations;
- hints visible before the independent attempt when the design claims progressive reveal;
- D2/D3 difficult ideas with only static text and no staged representation;
- Core (2) question numbers without an explicit family/method bridge.

### G8 — READINESS_AND_TRANSFER_AUDIT

Each released problem family needs a readiness gate covering four abilities:

1. **RECOGNISE** — identify the family from the question signals;
2. **REPRESENT** — draw/write the correct model without help;
3. **FIRST MOVE** — choose the first useful equation/condition without H2/H3;
4. **FINISH** — solve a fresh analogous problem and check the result.

Recommended release rule: 4/4 without H2/H3. Otherwise route the learner back to the named atom/routine.

### G9 — MACHINE_QA_AND_HANDOFF

Before handing off:
- run `tests/test_physics_core1a_production_kit.py`;
- run `production_kit/run_golden_fixtures.py`;
- run all existing Core1A tests;
- validate JSON files;
- confirm the target build manifest is `COMPLETE`;
- update build-state so `next_active_bucket` points to the next non-skipped bucket;
- add a PR progress comment only after CI passes.

## Golden production fixtures

The production kit's three fixtures are deliberately orthogonal:

- `fixtures/golden/M2D-SBA-03.json`: LOW load and a held cross-bucket release;
- `fixtures/golden/M2D-SBA-05.json`: VERY_HIGH load and seven transfer families;
- `fixtures/golden/M2D-SBA-21.json`: source-visible extension with explicit missing-theory boundary and derived bridges.

A future implementation may add more fixtures, but these three must continue to pass unless the contract version is intentionally bumped.

## Stop conditions

Do not continue rendering if any of these are true:

- task routing disagrees with durable build state;
- primary question ownership is ambiguous;
- source/answer contracts are missing or invalid;
- a Core (2) hint reveal has no prior teaching home;
- source support is unclear and the bridge would require invented physics;
- a derived bridge has no authorised derivation basis;
- a high-load bucket has not been split into sufficient problem families;
- scaffold visual-stage minima are not met;
- independent practice is missing or hints precede the attempt;
- readiness is missing or appears after Core (2) release;
- publication index is stale;
- the LR validator fails;
- the golden fixtures fail.

The goal is not to guarantee that a future agent never makes a mistake; the goal is to make deviations **visible, reproducible, testable and build-failing** rather than dependent on memory.
